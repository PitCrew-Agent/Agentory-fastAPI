# ADR-0013: RAG 검색 파이프라인 구성 결정 (청커·임베더·하이브리드·리랭커)

- 상태: 승인 대기
- 결정자: 김건
- 관련: [ADR-0001](0001-architecture.md) (임베딩·벡터 스토어 포트), [ADR-0012](0012-answer-quality-eval.md) (답변 품질 평가)

## 배경

RAG 검색 파이프라인은 청커, max_token, 임베딩 모델, 융합 방식, 리랭커라는 다섯 개 축을 가지며
각 축이 독립적으로 최적인 값을 고른다고 전체 최적이 되지 않습니다. 뒤 단계 실험은 앞 단계에서
확정한 값을 전제로 수행하므로, 후보가 좁혀진 경로를 한 문서에서 읽을 수 있어야 "왜 이 조합인가"가
설명됩니다. 본 ADR은 세 단계 실험 결과를 순서대로 기록합니다.

1단계는 검색 파이프라인을 전혀 쓰지 않고 청킹 자체의 품질만 재서 후보를 좁힙니다. 질의와 정답이
필요 없어 평가 셋 품질에 영향받지 않는 대신, 검색 성능을 직접 보장하지는 않습니다. 2단계는 1단계
상위 3개 후보를 실제 검색 지표로 검증하며 임베딩 모델을 함께 고릅니다. 3단계는 확정한 청커와
임베더 위에서 융합 방식과 리랭커를 비교합니다.

## 결정

| 축 | 선택 | 근거 |
| --- | --- | --- |
| 청커와 max_token | Docling HybridChunker 512 | BI·ICC·DCC 평균은 1위(0.7197)이나 세 지표 각각으로는 1위가 아니어서, max_token별 청킹 조합 상위 3개를 임베딩 모델 3종과 교차 평가한 뒤 검색 지표로 확정 |
| 임베딩 모델 | multilingual-e5-base (768차원) | 확정 청커와의 조합에서 recall@3·ndcg@10·MRR 세 지표 모두 1위 |
| 융합 방식 | convex (alpha 0.5) | 리랭커 병용 시 dense 단독 대비 recall@3 +1.3%p, ndcg@3 +1.1%p, MRR +0.8%p |
| 리랭커 **성능 1순위** | BGE reranker v2 m3 | recall@3·ndcg@3·MRR 3지표 일관 우세 |
| 리랭커 **운영 채택** | MiniLM | AWS 인프라 사양과 처리 속도 제약을 함께 고려한 선택 |

청커와 max_token은 별개의 축이 아니라 **하나의 조합으로 평가했습니다.** 청커마다 경계를 잡는
방식이 달라 같은 max_token이라도 결과가 달라지므로, 청커 4종과 max_token 3종을 곱한 10개 조합을
각각 측정했습니다. Docling Hierarchical은 max_token을 받지 않아 단일 값입니다.

**1단계 종합점수 1위가 곧 최종 선택은 아니었습니다.** Docling Hybrid 512가 종합 0.7197로 1위였지만
세 지표를 각각 보면 BI 2위, ICC 7위, DCC 4위로 어느 지표에서도 단독 1위가 아니었습니다. 종합점수는
산술평균이라 분산이 큰 BI에 좌우되는 값이기도 합니다. 그래서 1단계만으로 확정하지 않고 **상위 3개
조합**(Docling Hybrid 512, Haystack Recursive 512, Docling Hierarchical)을 2단계로 넘겨 실제 검색
지표로 검증한 뒤 확정했습니다.

## 방법론

### 내재적 지표 BI·ICC·DCC의 정의

세 지표는 Adaptive Chunking 논문의 정의를 따랐습니다. 검색을 수행하지 않고 청킹 결과 자체만으로
계산하므로, 질의와 정답 라벨이 없어도 청커를 비교할 수 있습니다.

**BI(Block Integrity, 블록 무결성)** 는 파서가 인식한 블록을 청크 경계가 자르지 않은 비율입니다.
여기서 블록은 문단과 표와 목록처럼 파서가 하나의 의미 단위로 판정한 덩어리입니다. Docling 계열
청커는 같은 블록 참조가 여러 청크에 걸쳐 나타나는지로, 문자 좌표 기반 청커는 블록 시작 좌표와 청크
시작 좌표를 대조해 판정합니다. 1.000이면 어떤 블록도 절단되지 않았다는 뜻이고, 표가 중간에서
잘리면 값이 내려갑니다. 임베딩을 쓰지 않으므로 임베딩 모델을 바꿔도 값이 변하지 않습니다.

**ICC(Intra-Chunk Cohesion, 청크 내부 응집도)** 는 한 청크 안의 문장들이 그 청크 전체와 얼마나
같은 주제인지를 재는 값입니다. 청크를 문장 단위로 나눠 각 문장 임베딩과 청크 임베딩의 코사인
유사도를 평균합니다. 문장이 하나뿐인 청크는 자기 자신과의 비교가 되므로 제외합니다. 값이 높으면
한 청크가 한 가지 이야기만 담고 있다는 뜻입니다.

**DCC(Document Contextual Coherence, 문서 문맥 일관성)** 는 청크가 앞뒤 문맥과 얼마나 이어지는지를
재는 값입니다. 인접한 청크들을 토큰 예산 3000 안에서 이어 붙여 문맥 창을 만들고, 그 창의 임베딩과
창에 속한 각 청크 임베딩의 코사인 유사도를 평균합니다. 값이 높으면 청크가 문서 흐름에서 고립되지
않았다는 뜻입니다.

세 지표는 서로 상충합니다. 청크를 잘게 자르면 문장들이 서로 비슷해져 ICC는 오르지만 블록을 더 많이
절단해 BI가 떨어지고 앞뒤 문맥과도 멀어져 DCC가 떨어집니다. 크게 자르면 BI와 DCC가 오르는 대신
한 청크에 여러 주제가 섞여 ICC가 떨어집니다. 종합점수는 세 값의 산술평균이며, 어느 한 지표만 높은
청커가 아니라 절충이 잘 된 청커를 고르기 위한 값입니다.

### 하이브리드 융합 방식 convex와 combmnz의 정의

두 방식 모두 dense 검색 점수와 BM25 어휘 검색 점수를 합치는 **점수 기반 융합**입니다. 순위만 쓰는
RRF와 달리 점수 크기를 그대로 활용하므로, 합치기 전에 척도를 맞추는 정규화가 필수입니다. dense는
코사인 유사도라 -1~1 범위이지만 BM25는 상한이 없어서 그대로 더하면 BM25가 결과를 지배합니다.

**정규화.** 각 검색기가 돌려준 후보 집합 안에서 min-max 정규화를 적용합니다.

```
s~(d) = (s(d) - min_s) / (max_s - min_s)
```

전 항목이 동점이면 모두 1.0으로 둡니다. 다만 min-max는 최저 점수를 정확히 0으로 만들기 때문에
"등장했지만 최하위"와 "아예 등장하지 않음"이 구분되지 않습니다. 그래서 등장한 후보에는 1e-6의
하한을 둬 미등장(0.0)과 구분합니다. 이 하한이 있어야 alpha를 1.0으로 놓았을 때 dense 단독과 정확히
같은 순서로 환원됩니다.

**convex 결합.** 정규화한 두 점수를 가중 합산합니다. 한쪽 리스트에만 등장한 후보는 반대쪽 점수를
0으로 둡니다.

```
score_convex(d) = alpha x dense~(d) + (1 - alpha) x sparse~(d),    0 <= alpha <= 1
```

alpha는 dense 비중이며 1이면 dense 단독, 0이면 BM25 단독으로 환원됩니다. 현재는 0.5로 두 신호를
같은 비중으로 봅니다. 가중치가 하나라 신호 비중을 직접 조절할 수 있다는 점이 운영상 장점입니다.

**combmnz.** 정규화한 두 점수를 더한 뒤, 그 문서를 반환한 검색기의 수를 곱합니다.

```
score_combmnz(d) = (dense~(d) + sparse~(d)) x n(d),
n(d) = 그 문서가 등장한 리스트 수 (dense에만 또는 sparse에만 있으면 1, 양쪽에 있으면 2)
```

곱해지는 `n(d)`가 이 방식의 핵심입니다. 두 검색기가 함께 찾아낸 문서에 보너스를 줘서, 서로 다른
원리로 동작하는 검색기가 동의했다는 사실 자체를 신호로 취급합니다. 대신 비중을 조절할 파라미터가
없습니다.

**두 식의 관계.** alpha가 0.5일 때 `score_combmnz(d) = 2 x n(d) x score_convex(d)`가 성립합니다.
양쪽에 등장한 문서는 `n=2`라 4배, 한쪽에만 등장한 문서는 `n=1`이라 2배가 되므로, combmnz는
convex(0.5) 대비 **양쪽 등장 문서를 정확히 2배 더 밀어 올립니다.** 정규화 점수가 다음과 같을 때의
차이를 보면 분명합니다.

| 문서 | dense~ | sparse~ | convex(0.5) | combmnz |
| --- | ---: | ---: | ---: | ---: |
| A (양쪽 등장) | 0.3 | 0.3 | 0.30 (3위) | (0.3+0.3) x 2 = **1.20 (1위)** |
| B (dense만) | 1.0 | 미등장 | **0.50 (공동 1위)** | 1.0 x 1 = 1.00 (공동 2위) |
| C (sparse만) | 미등장 | 1.0 | **0.50 (공동 1위)** | 1.0 x 1 = 1.00 (공동 2위) |

한쪽에서 최고점을 받은 B·C와, 양쪽에서 중간 점수를 받은 A의 순위가 뒤집힙니다. 실제 M-3에서 리랭커
없이 combmnz가 convex보다 낮았던 것(recall@3 0.661 대 0.679)도 이 성향 차이로 설명됩니다.

### 지표 성격이 다른 두 축을 분리해 기록합니다

1단계의 BI·ICC·DCC는 **내재적 지표**로, 청크와 문장과 문맥 창의 임베딩 사이 코사인 유사도이며
검색을 수행하지 않습니다. 2단계와 3단계의 recall·ndcg·MRR은 **외재적 지표**로, 실제 검색 결과가
골든 근거를 회수했는지 판정합니다. 단위와 판정 기준이 다르므로 같은 표에 섞지 않습니다.

### 1단계 평가 임베더를 서비스 임베더와 분리했습니다

ICC·DCC 계산에는 OpenAI `text-embedding-3-large`(1024차원)를 심판 임베더로 썼습니다. 서비스
임베더(e5-base)로 청킹을 평가하면 특정 임베더에 유리한 청킹이 선택될 수 있어, 후보 선정 단계에서는
서비스와 분리된 상위 모델을 기준으로 삼았습니다. BI는 파서 블록을 청크 경계가 잘랐는지 세는
지표라 임베딩 모델과 무관하며, 임베더를 바꿔도 값이 변하지 않습니다.

### 단계별 통제 변수

| 단계 | 코퍼스 | 평가 셋 | 고정한 값 |
| --- | --- | --- | --- |
| 1단계 (M-1) | 매뉴얼·가이드라인·SOP 3종 PDF, Docling 파싱 | 없음 (내재적) | 심판 임베더 text-embedding-3-large 1024, DCC 창 3000토큰 |
| 2단계 (M-2) | 동일 3종 문서 (Markdown 변환) | span relevance | 상위 3개 청커, 리랭커 미사용 |
| 3단계 (M-3) | 동일 3종 문서 PDF 원천 155청크 | span relevance | 청커 Docling Hybrid 512, 임베더 e5-base, 후보 풀 N=10, alpha 0.5, k=3 |

## 측정

### M-1. 청커 x max_token 내재적 품질 (BI·ICC·DCC)

문서 3종 x 청커 4종 x max_token 3종의 전체 결과이며, 종합점수(BI·ICC·DCC 산술평균) 내림차순입니다.
문서별 점수를 동일 가중으로 평균했습니다.

| 청커 | max_token | BI | ICC | DCC | 종합점수 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Docling Hybrid | 512 | 0.9853 | 0.5544 | 0.6194 | **0.7197** |
| Haystack Recursive | 512 | 0.9741 | 0.4882 | 0.6841 | 0.7155 |
| Docling Hierarchical | natural | 1.0000 | 0.6237 | 0.5055 | 0.7097 |
| Docling Hybrid | 256 | 0.9191 | 0.5876 | 0.5796 | 0.6954 |
| Chonkie Recursive | 512 | 0.8486 | 0.4670 | 0.7075 | 0.6744 |
| Haystack Recursive | 256 | 0.8768 | 0.5558 | 0.5834 | 0.6720 |
| Docling Hybrid | 128 | 0.7349 | 0.6330 | 0.5333 | 0.6337 |
| Chonkie Recursive | 256 | 0.7163 | 0.5159 | 0.6314 | 0.6212 |
| Haystack Recursive | 128 | 0.6849 | 0.6370 | 0.5189 | 0.6136 |
| Chonkie Recursive | 128 | 0.6051 | 0.6144 | 0.5423 | 0.5872 |

max_token이 작아질수록 BI가 급격히 떨어지고 ICC는 올라갑니다. 청크를 잘게 자르면 내부 문장들이
서로 비슷해져 응집도는 오르지만, 파서가 인식한 표와 문단을 그만큼 더 많이 절단하기 때문입니다.
128 구간에서 BI가 0.6051~0.7349까지 내려가는 것이 그 결과이며, 종합점수 하위 4개가 모두 128·256
구간인 이유이기도 합니다.

Docling Hierarchical은 BI가 1.0000으로 완벽하지만 DCC가 0.5055로 가장 낮습니다. 파서 블록을 그대로
청크로 쓰기 때문에 경계를 전혀 자르지 않는 대신, 청크가 너무 잘게 나뉘어 앞뒤 문맥과의 일관성이
약합니다. Docling Hybrid 512는 BI 2위와 DCC 4위이고 ICC는 7위인데도 종합 1위인데, 이는 세 지표의
분산이 다르기 때문입니다. BI는 0.6051에서 1.0000까지 0.3949 범위로 벌어지는 반면 ICC는 0.1700,
DCC는 0.2021 범위에 그쳐, 산술평균 종합점수는 사실상 BI가 좌우합니다. 종합점수를 볼 때는 이
가중 불균형을 함께 읽어야 하며, ICC 열위가 큰 손실이 아니라는 판단은 M-2의 검색 지표로 확인했습니다.

### M-2. 상위 3개 후보 x 임베딩 모델 3종 검색 품질

M-1 상위 3개 후보를 각각 임베딩 모델 3종으로 적재해 측정한 전체 결과입니다. 1위는 recall@3와
ndcg@10과 MRR 세 지표 모두에서 앞선 Docling Hybrid 512와 e5-base 조합입니다. 나머지 조합은
지표마다 순서가 엇갈려 하나의 지표로 줄 세울 수 없으므로, 두 조합을 맞대어 **세 지표 중 둘 이상에서
앞서는 쪽을 위에 두는 방식**으로 정렬했습니다. 이 규칙으로 9개 조합의 순위가 동점 없이 정해집니다.

| 청커 | 임베더 | recall@3 | ndcg@10 | MRR |
| --- | --- | ---: | ---: | ---: |
| Docling Hybrid 512 | e5-base 768 | **0.637** | **0.649** | **0.593** |
| Haystack Recursive 512 | granite-r2 768 | 0.603 | 0.618 | 0.555 |
| Haystack Recursive 512 | e5-base 768 | 0.614 | 0.612 | 0.539 |
| Docling Hybrid 512 | granite-r2 768 | 0.586 | 0.602 | 0.545 |
| Docling Hierarchical | e5-base 768 | 0.559 | 0.575 | 0.520 |
| Haystack Recursive 512 | openai small 1536 | 0.567 | 0.549 | 0.479 |
| Docling Hybrid 512 | openai small 1536 | 0.535 | 0.529 | 0.467 |
| Docling Hierarchical | granite-r2 768 | 0.440 | 0.520 | 0.464 |
| Docling Hierarchical | openai small 1536 | 0.445 | 0.451 | 0.394 |

Haystack Recursive 512와 granite 조합이 같은 청커의 e5 조합보다 위에 있는 것이 이 규칙의
예입니다. recall@3만 보면 0.603 대 0.614로 뒤지지만 ndcg@10과 MRR에서 앞서므로 세 지표 중
둘에서 우세합니다.

M-1 종합점수 1위였던 Docling Hybrid 512가 검색 지표에서도 1위이고, 상위 세 후보 중 3위였던
Docling Hierarchical은 임베더 3종 모두에서 최하위권입니다. 내재적 지표로 후보를 좁힌 판단이
외재적 지표와 어긋나지 않았습니다. Docling Hybrid 512와 e5-base 조합이 세 지표에서 모두
1위여서 이 조합을 최종 선택했습니다.

최종 청커인 Docling Hybrid 512에서는 e5-base가 granite보다 recall@3, ndcg@10, MRR이 모두
높았습니다. OpenAI small은 세 청커 모두에서 뒤처졌습니다. e5를 택한 이유는 최종 청커와 묶었을 때
최고 상위 순위 지표를 냈다는 점과, 768차원으로 기존 1536차원 기준선보다 저장·인덱스 비용이 작다는
점입니다.

### M-3. 하이브리드 융합 x 리랭커 9조합

융합 3종과 리랭커 3종(미사용 포함)의 전체 조합입니다. recall@3와 ndcg@3와 MRR 세 지표가 모두
같은 순서를 보여 그 순서대로 정렬했으며, 판단도 세 지표를 함께 봤습니다. 청커와 임베더는 M-2에서
확정한 Docling Hybrid 512와 e5-base로 고정했습니다.

| 융합 | 리랭커 | recall@3 | ndcg@3 | MRR |
| --- | --- | ---: | ---: | ---: |
| convex | BGE | **0.789** | **0.772** | **0.771** |
| combmnz | BGE | **0.789** | **0.772** | **0.771** |
| none (dense) | BGE | 0.776 | 0.761 | 0.763 |
| convex | MiniLM | 0.758 | 0.729 | 0.724 |
| combmnz | MiniLM | 0.758 | 0.729 | 0.724 |
| none (dense) | MiniLM | 0.734 | 0.711 | 0.716 |
| none (dense) | 미사용 | 0.694 | 0.617 | 0.613 |
| convex | 미사용 | 0.679 | 0.589 | 0.601 |
| combmnz | 미사용 | 0.661 | 0.578 | 0.597 |

운영은 항상 리랭커를 사용하므로 의사결정 기준은 리랭커 병용 조건입니다. 그 조건에서 하이브리드
융합은 dense 단독보다 recall@3이 1.3%p 높습니다.

**convex와 combmnz는 리랭커를 붙이면 소수점 셋째 자리까지 완전히 같습니다.** 두 융합의 상위 10개
후보 집합이 같고 순서만 다른데, 리랭커가 그 10개를 다시 정렬하므로 차이가 흡수됩니다. 융합 방식
선택에 품질상 실익이 없어 alpha로 신호 비중을 직접 조절할 수 있는 convex를 승계했습니다.

리랭커는 두 축을 나눠 기록합니다.

**성능 1순위는 BGE입니다.** MiniLM보다 recall@3 +3.1%p, ndcg@3 +4.3%p, MRR +4.7%p로 세 지표가
일관되게 우세합니다. 품질만 놓고 고르면 BGE입니다.

**운영 채택은 MiniLM입니다.** 로컬 모델 캐시가 BGE 약 2.14GB, MiniLM 약 470MB로 BGE가 4.7배
큽니다. 배포 대상인 AWS Fargate는 GPU 없이 CPU로 추론하며, 이 조건에서 실측 지연이 BGE 약 17초,
MiniLM 약 3초로 벌어집니다. 챗봇 검색 경로의 리랭커 제한 시간은 10초, 장애 대응 계획 수립 경로의
매뉴얼 검색 제한은 5초라서 BGE를 기본값으로 두면 제한 시간에 걸려 리랭킹이 통째로 폴백되거나
매뉴얼 근거가 빠집니다. 인프라 사양과 처리 속도를 함께 고려해 MiniLM을 운영 기본값으로
채택했습니다.

## 한계

**1. 평가 문서가 실제 현장 문서가 아닙니다.** 세 문서는 생성형 AI의 도움을 받아 Markdown으로 작성한
뒤 PDF로 렌더링한 것이라 레이아웃이 깔끔합니다. 실제 설비 매뉴얼과 SOP에는 사진과 도면,
스캔된 표, 작성자 결재란과 서명, 수기 주석이 섞여 있지만 이 문서에는 없습니다.

특히 **OCR이 필요하지 않았습니다.** 대상 PDF는 전부 텍스트 레이어를 갖고 있고 이미지 XObject가
0개여서 OCR을 끈 채로 파싱했습니다. 실제 문서였다면 스캔본과 사진 속 표를 읽어내는 OCR 품질이 파싱
결과를 크게 좌우했을 텐데, 이번 실험에서는 그 변수가 아예 빠졌습니다. 최근 파서가 VLM과 딥러닝
레이아웃 모델로 얻는 이점도 바로 그런 요소를 읽어내는 데서 나오는데, 이번 코퍼스는 그 능력을
요구하지 않습니다.

따라서 M-1의 BI가 전반적으로 높게 나온 것은 파서와 청커의 실력이라기보다 문서가 쉬웠다는 뜻으로
읽어야 하며, 실제 문서에서는 파서 선택의 중요도가 지금보다 커질 수 있습니다.

**2. max_token을 512까지만 평가했습니다.** 서비스 임베더 후보인 multilingual-e5-base의 입력 상한이
512 토큰이라 그 위 구간은 애초에 쓸 수 없었습니다. 다른 임베딩 모델은 수천에서 수만 토큰까지
받으므로 1024 이상 구간에서 결과가 달라질 수 있습니다. 그럼에도 e5를 후보로 유지한 이유는 대상
문서가 한국어 위주이면서 알람 코드와 장비 부품명 같은 핵심 용어는 영어로 적혀 있어, 두 언어를 같은
공간에 태우는 다국어 모델이 필요했기 때문입니다.

**3. max_token과 청커와 임베딩 모델을 한 번에 교차 평가하지 못했습니다.** 세 축을 모두 곱하면 조합이
빠르게 늘어나는데 각 조합마다 재적재와 재평가가 필요해 시간이 부족했습니다. 대신 내재적 지표로
청커와 max_token을 먼저 좁히고, 상위 3개 후보에 대해서만 임베딩 모델을 교차한 단계별 설계를
택했습니다. 각 단계는 공정하게 통제했지만 전역 최적 조합을 탐색한 것은 아닙니다.

**4. 융합 가중치 alpha는 0.5만 평가했습니다.** dense와 BM25를 같은 비중으로 둔 한 점만 측정했을 뿐
다른 값으로 스윕하지 않았으므로, convex의 최적 alpha가 0.5라는 근거는 없습니다.

**5. 후보 풀 N과 최종 k도 한 값씩만 썼습니다.** 실무에서 이 두 숫자는 서비스 성격에 따라 넓게
달라지는데, 이번에는 N=10과 k=3 하나씩만 측정했습니다. 다만 두 값이 고정된 이유는 서로 다릅니다.

N은 **인프라 사양 때문에 늘리지 못했습니다.** 리랭커는 후보를 재정렬만 하므로 N 안에 정답이 없으면
어떤 리랭커도 만회할 수 없고, 따라서 N은 회수율 상한을 직접 정하는 값입니다. 그런데 CPU 추론
지연이 N에 거의 비례해서, MiniLM 기준 N=10에 약 3초인 지연이 N을 두 배로 올리면 장애 대응 경로의
매뉴얼 검색 제한 5초를 넘습니다. GPU가 있거나 상위 인스턴스를 쓸 수 있는 조건이라면 N을 20 이상으로
올려 회수율 상한 자체를 높이는 실험이 가능하며, 이는 인프라 제약이 풀릴 때 가장 먼저 다시 볼
항목입니다.

k는 **비교 자체를 하지 않았습니다.** 검색 단계 지표는 k=3·5·7·10을 함께 산출했지만 운영 판단은
k=3 기준으로만 내렸고, k를 3·4·5로 바꿨을 때 최종 답변의 정확성과 환각이 어떻게 달라지는지는
측정하지 않았습니다. 근거를 더 넣으면 답변이 좋아지는지, 아니면 불필요한 근거가 섞여 오히려
나빠지는지는 이 실험으로 답할 수 없습니다.
