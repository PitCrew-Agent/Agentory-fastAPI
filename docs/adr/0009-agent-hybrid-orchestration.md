# ADR-0009: 에이전트 하이브리드 오케스트레이션 전환 (Planner + 병렬 Fetch + Fast Router)

- 상태: 승인 (2026-07-20)
- 결정자: 주희정
- 관련: [ADR-0001](0001-architecture.md), [ADR-0003](0003-agent-runtime-budget.md), [docs/agent/architecture.md](../agent/architecture.md), feature/139-agent-hybrid-orchestration(#140), feature/139-architecture-doc(#142), feature/148-orchestrator-followups(#149), feature/166-orchestrator-default-on(#167)

## 배경

[ADR-0001](0001-architecture.md)은 에이전트를 **Supervisor + 워커 ReAct** 구조로 정하고 이를
FastAPI 앱 in-process로 두기로 했습니다. [ADR-0003](0003-agent-runtime-budget.md)은 그 구조를
운영 가능한 품질로 만들기 위한 런타임 가드레일(컨텍스트 상한·반복 예산·후처리)을 추가했습니다.

가드레일로 실패는 막았으나 지연과 비용 자체는 구조에서 나오는 것이라 해결되지 않았습니다.
Supervisor가 매 턴 라우팅 LLM을 호출하고, 선택된 워커가 다시 자기 ReAct 루프를 돌며, 워커가
3종(realtime·knowledge·maintenance)으로 늘면서 라우팅 왕복이 직렬로 쌓였습니다. 매 호출마다
히스토리를 재전송하므로 입력 토큰도 왕복 수에 비례해 증가했습니다.

본 ADR은 이 구조를 **Planner 1회 + 병렬 Fetch + 제한 ReAct**로 교체한 결정과 그 실측 근거를
기록합니다. 그래프 구조 자체의 서술은 [docs/agent/architecture.md](../agent/architecture.md)에
있으며, 본 ADR은 왜 교체했는지와 얼마나 개선되었는지를 다룹니다.

## 결정

### 1. Supervisor 라우팅과 워커 선택을 Planner 한 노드로 통합 (#140)

모든 MCP 도구를 bind한 단일 에이전트(`supervisor/orchestrator.py`의 `make_planner_node`)가
라운드마다 필요한 도구를 스스로 골라 emit하고, `make_fetch_node`가 이를 `asyncio.gather`로
병렬 실행합니다. 라우팅 LLM 호출과 워커 진입 호출이 사라지고, 독립 근거(센서 로그와 정비 이력
등)는 한 라운드에 겹쳐 실행됩니다.

앞선 결과에 의존하는 근거는 관찰 후 다음 라운드에 호출하며, 이 재판단이 ReAct 루프에
해당합니다. 재판단 라운드 예산은 하드코딩하지 않고 `agent_fetch_rounds_max`(기본 3)로 두어
소진 시 LLM 호출 없이 확보된 근거로 종료합니다.

### 2. Fast Router는 오케스트레이터와 독립된 축으로 유지 (#140)

인사·감사·잡담은 데이터 수집이 필요 없으므로, 정규식 규칙으로 분류해 Finalizer로 직행시킵니다
(`agent_fast_router_enabled`, 기본 on). 이 플래그는 `agent_orchestrator_enabled`와 독립이며,
두 축을 분리한 것은 의도한 설계입니다. 바이패스는 오케스트레이터 채택 여부와 무관하게 유효한
최적화이기 때문입니다. 다만 이 독립성 때문에 아키텍처 A/B만으로는 바이패스 효과가 측정되지
않으며, 이는 아래 3-3에서 별도 벤치로 분리했습니다.

### 3. 기본값을 오케스트레이터 on으로 전환 (#167)

측정으로 개선이 확인되고 골든 E2E가 두 경로 모두에서 통과한 뒤
(`100e65d` 골든 E2E 파라미터화), `agent_orchestrator_enabled` 기본값을 true로 바꿨습니다.
레거시 경로는 삭제하지 않고 플래그로 남겨 회귀 시 즉시 되돌릴 수 있게 했습니다.

### 3-3. Fast Router 축 분리 측정

3-1의 A/B는 `orchestrator_enabled` 축이라 Fast Router가 양쪽 모두 켜진 채로 측정되었고, 그
결과 `smalltalk` 질의가 양쪽 모두 호출 1.0회·입력 353토큰으로 동일하게 나왔습니다. 바이패스
효과가 측정에서 빠져 있었다는 뜻입니다. 이를 분리하기 위해 `scripts/bench/fast_router_bench.py`를
추가해 `fast_router_enabled` 축으로 다시 측정했습니다(2026-07-20, 질의 3종 x 3회).

아래는 3-4절의 오탐 수정을 반영한 뒤 재측정한 값입니다.

| 질의 | 지표 | Fast Router off | Fast Router on | 개선 |
| --- | --- | --- | --- | --- |
| 잡담 2종 | 평균 지연 | 4.21s | 2.63s | -37.4% |
| 잡담 2종 | LLM 호출 | 2.0회 | 1.0회 | -50.0% |
| 잡담 2종 | 입력 토큰 | 1,765 | 348 | -80.3% |
| 잡담 2종 | 질의당 비용 | $0.00087 | $0.00041 | -52.6% |
| diag_guard | p50 지연 | 28.45s | 26.92s | 회귀 없음 |

바이패스는 잡담 질의의 라우팅 LLM 왕복 1회를 통째로 제거해 입력 토큰을 80% 줄입니다. 오탐 수정
이후에도 호출수·토큰 개선 폭은 -50.0%·-80.3%로 동일하므로, 가드 추가가 바이패스 이득을 훼손하지
않았음을 확인했습니다.

수정 전 측정에서는 회귀 가드로 넣은 진단 질의(`diag_guard`)가 on 쪽에서 오히려 느리게
나왔습니다(p50 31.17s 대 44.10s). 호출수는 4.0회에서 3.3회로 줄어 경로가 늘어난 것은 아니었기에
n=3의 응답 지연 편차로 보고 판단을 유보했는데, 재측정에서 역전이 사라져(28.45s 대 26.92s)
노이즈였음이 확인되었습니다. 표본이 작은 구간에서 단일 측정으로 결론을 내리지 않은 판단은
유지할 만합니다.

잡담 지연 개선 폭이 -43.1%에서 -37.4%로 줄어든 것은 on이 느려져서가 아니라 off 쪽이 6.32s에서
4.21s로 빨라진 결과입니다(on은 3.59s에서 2.63s로 함께 빨라졌습니다). 역시 n=3 편차 범위로 봅니다.

### 3-4. 규칙 분류 정확도와 발견된 결함

Fast Router의 `classify_intent`는 LLM을 쓰지 않으므로 라벨 세트로 비용 없이 채점할 수 있습니다.
최초에는 규칙을 보고 만든 질의 14건으로 채점해 정확도 1.000이 나왔으나, 이는 규칙이 처리하도록
설계된 입력만 넣은 자기충족적 결과였습니다. 규칙이 깨질 만한 적대적 케이스 4건을 추가해 다시
채점한 결과는 다음과 같습니다.

| 지표 | 초기 세트 (n=14) | 적대적 케이스 추가 (n=18) | 수정 후 (n=18) |
| --- | --- | --- | --- |
| 정확도 | 1.000 | 0.778 | 1.000 |
| direct 재현율 | 1.000 | 1.000 | 1.000 |
| diagnostic 재현율 | 1.000 | 0.667 | 1.000 |
| 치명 오탐 (diagnostic을 direct로) | 0건 | 4건 | 0건 |

뚫린 4건은 모두 같은 패턴입니다.

```
"고마워, 근데 아까 그 값 다시 보여줄래?"   → direct  (기대: diagnostic)
"감사합니다. 어제 것도 뽑아주세요"          → direct  (기대: diagnostic)
"수고했어, 방금 그거 그래프로 그려줘"       → direct  (기대: diagnostic)
"안녕, 그 다음 건 어떻게 됐어?"            → direct  (기대: diagnostic)
```

지시대명사로 앞 맥락을 참조하는 후속 턴 질의는 진단 키워드가 문장에 없고 인사·감사 표현만 있어
`direct`로 분류되며, 데이터 수집 없이 Finalizer로 직행했습니다. 모듈이 선언한 "애매하면 diagnostic
유지" 원칙이 이 구간에서 지켜지지 않았습니다. 원인은 규칙이 대화 이력을 보지 않고 마지막 발화만
검사하는 구조(`_last_user_text`)입니다.

수정은 별도 작업(feature/193-fast-router-followup)으로 분리해 두 가지 가드를 추가했습니다.

- `_FOLLOWUP_REFERENCE`: 지시대명사·시점 참조(그거·아까·방금·어제·다시 등)가 있으면 인사 표현이
  섞여 있어도 `diagnostic` 유지
- `_REQUEST_CLAUSE`: 잡담 신호가 접두부에 그치고 뒤에 요청절(보여·알려·뽑아·그려 등)이 이어지면
  순수 잡담이 아니라고 보아 `diagnostic` 유지

수정 후 같은 라벨 세트로 재채점한 결과 정확도 1.000, 치명 오탐 0건으로 회복했습니다. direct
재현율이 1.000을 유지하므로 잡담이 진단 경로로 새는 반대 방향 손실도 없습니다. 다만 이 가드는
여전히 **단일 발화 규칙**이며 대화 이력을 참조하지 않습니다. 위 표현 목록에 없는 방식으로 앞
맥락을 참조하는 질의는 같은 유형의 오탐이 재발할 수 있으므로, 라벨 세트를 회귀 케이스로 유지해
규칙 변경 시마다 재채점합니다(`194e965`에서 테스트로 고정).

### 3-5. 재측정 경위 (2026-07-15 → 2026-07-20)

최초 측정은 2026-07-15에 질의 3종 x 3회(설정당 n=9)로 수행했고, 그 수치가
[docs/agent/architecture.md](../agent/architecture.md) §2.2에 실려 있었습니다. 본 ADR 작성 시점에
그대로 인용하지 않고 재측정한 이유는 두 가지입니다.

첫째, 이후 병합된 #190(챗봇 되묻기 제거·프롬프트 정합)과 #192(기간 지정 조회 구간 집계 전환)가
모두 토큰·지연에 직접 영향을 주는 변경이었습니다. 둘째, 최초 워크로드에 잡담 질의가 없어 Fast
Router 경로가 측정 대상에서 빠져 있었습니다.

재측정 결과 양쪽 경로 모두 무거워졌습니다.
